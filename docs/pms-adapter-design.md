PMS Adapter Design Document

Status: ProposedTarget PMS: Oracle OPERA Cloud (or standard REST-based Cloud PMS)
1. Target PMS API

    Protocol: REST (JSON over HTTPS).
    Base URL: Configured via environment variable (e.g., PMS_API_BASE_URL).
    Rationale: Modern cloud PMS systems (Opera Cloud, Mews, Cloudbeds) universally expose REST APIs. This avoids the fragility of direct SQL views and the verbosity of SOAP.

2. Authentication Method

    Method: OAuth 2.0 Client Credentials Flow.
    Implementation: The adapter will request a bearer token from the PMS token endpoint using a client_id and client_secret stored in environment variables.
    Token Caching: The token will be cached in memory with its expiration time. The adapter will automatically fetch a new token if the current one is expired or within 60 seconds of expiring.

3. Timeout Policy

To prevent the chatbot from hanging during PMS outages, strict timeouts are enforced at the httpx client level:

    Read Operations (GET): 3 seconds.
        Rationale: Users expect quick responses for arrivals/room status. If it takes longer, we fail fast.
    Write Operations (POST/PUT): 5 seconds.
        Rationale: Writes (mark room clean, resolve incident) may take slightly longer to process on the PMS side, but still must not block the user indefinitely.

4. Retry Policy

    Scope: Applied only to idempotent read operations (GET) as defined in the PMSInterface.
    Conditions: Retries will trigger on httpx.ConnectTimeout, httpx.ReadTimeout, or 5xx Server Error responses.
    Strategy: Exponential backoff with jitter.
        Attempt 1: Immediate
        Attempt 2: Wait 0.5s
        Attempt 3: Wait 1.2s
    Limit: Maximum of 3 total attempts.
    Writes: Write operations (mark_room_clean, resolve_incident) will never be automatically retried by the HTTP client to prevent duplicate writes (even if marked idempotent in our interface, network-level retries on writes require explicit distributed locking).

5. Operation ID Strategy

To handle the distributed-transaction gap (e.g., PMS succeeds, but our local DB audit fails):

    Every request sent to the PMS API will include a custom header: X-Operation-Id: <uuid4>.
    This UUID will be generated by our application at the start of the command execution and stored in the local audit log before the HTTP request is made.
    If the local transaction fails after the PMS succeeds, administrators can use the X-Operation-Id to query the PMS logs and reconcile the state without duplicating the operation.

6. Audit Semantics for "PMS succeeded, local failed"

If the adapter receives a 200 OK from the PMS, but the local database commit for the audit log fails (e.g., DB disconnect):

    Response to User: The API will return a 206 PARTIAL_CONTENT or a specific WARNING kind to the user: "Action completed on PMS, but local audit failed. Staff should verify manually."
    Error Logging: The full response payload from the PMS and the generated X-Operation-Id will be dumped to the application's standard ERROR log.
    Reconciliation: A background job or manual script will query the error logs for failed audits and use the X-Operation-Id to safely sync the local database state with the PMS state without re-triggering the write.
